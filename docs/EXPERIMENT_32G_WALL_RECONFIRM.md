# 实验:32G 墙再确认(反观测错误)

> 2026-08-11 立项。动机:主线正在狩猎 GSP 固件补丁来修 32G 墙,但历史上关于"墙"的
> 观测记录互相矛盾——有"vec_scan2 48 必现 845545477 坏单元"的失败记录,也有
> "单笔 72G 分配+写 OK""洞上 20.9G 单独正常"的成功记录。**如果墙为真,连续 60G+
> 的大对象必然自我污染,不可能全绿**。在继续烧补丁实验之前,必须用无混叠干扰的
> 方法论把地面真相重新打实。

## 0. 背景与受质疑的历史记录

| 记录 | 出处 | 疑点 |
|---|---|---|
| vec_scan2 48 → total_bad_units=845545477 | 多次复现,stock 基线 | 唯一硬性失败证据,但工具只测单对象自洽性,未曾刻画因果与 delta |
| "单笔 72G 分配+写 OK(74G OOM)" | FIX_PLAN_RECLAIM.md(2026-08-08,热加载态) | 72G 对象必跨 PA 32G;墙为真则高位写必踩低位,全量校验不可能通过 |
| "右(洞上)20.9G 单独正常" | PROBLEM_32G_WALL.md §4 | 高写低混叠下,"正常"可能只是踩到了无人校验的空闲低区 |
| "drip 72G 全程无幻影命中" | 同上 | drip 是慢速分配,校验覆盖与时机存疑 |

**关键理论点(实验设计的核心)**:如果写和读按同一规则混叠(写 X→X−32G,读
X←X−32G),那么**单对象写后自读永远自洽**,什么错都测不出来;伤害只会落在共享
混叠单元的**其他数据**上。vec_scan2 之所以能测到坏,是因为单个 48G 对象内部的
高区写把**同对象的低区**踩了。因此:

- "单对象写读全绿" **不能**作为墙不存在的证据;
- 判定墙的存在必须用**金丝雀对象**(先低后高、跨对象污染)或**对象内交叉污染**
  (先写低区模式 L、再写高区模式 H、回头验低区)。

## 1. 环境与约束

- 机器:p3-server,CMP 170HX(10G SKU,80G 几何),驱动 610.43.02 + cmpunlocker
  生产补丁(**5G 幻影洞 [36G,41G) 默认开**,保持开;`RMCmpPhantomReserve=0` 会
  在 74G 分配时必死 GSP,**禁止**)。
- GPU 当前健康:`nvidia-smi` 显示 81920 MiB。
- **服务器没有 nvcc**。新工具只能用主机侧代码:gcc + cudart(模式见
  `~/f0/f0_build.sh`:头文件和库来自 `~/vllm-env/.venv/.../nvidia/cu13`)。
  模式写读用 pinned host buffer + cudaMemcpy 分块(256MB)完成,不需要 kernel。
  若必须用 kernel,只能复用 `~/f0/` 已有二进制。
- 每个用例前做一次干净驱动重载(FLR 序列见 §5),避免跨用例污染与 FB 残留干扰。
- 任何用例中 dmesg 出现 Xid / GSP 死 → 该用例结果作废,FLR 后重来。

## 2. 统一工具规范(新写,~200 行 C)

`~/f0/wall_reconfirm.c`(gcc + cudart 编译):

1. `cuMemGetAddressRange` 打印每个分配对象的 VA 基址(判断落在洞下/洞上的依据)。
2. 写模式:64 位 `pat(addr) = addr * 0x9E3779B97F4A7C15 ^ (addr >> 3)`(或等价
   强混合 hash),按 256MB 块 host 生成 → cudaMemcpy HtoD。
3. 校验:DtoH 分块读回,host 比对;每个失配记录 (addr, expected, actual),
   并现场检验三个假设:
   - H1:actual == pat(addr − 32G)(恒定 −32G 混叠签名)
   - H2:actual == pat(addr mod 4G)(32 位截断签名)
   - H3:actual == 其他可识别模式(另一对象的 canary 值等)
4. 输出:每 1G 桶错误数直方图 + 前 20 个失配样本的假设检验结果 + 总计。

## 3. 用例矩阵

### P0 — 基线复现(必须最先做)
```
cd ~/f0 && sudo ./vec_scan2 48   # 连跑 3 次
```
预期:total_bad_units=845545477(或稳定值)。记录每桶直方图。
**若三次结果不一致 → 墙本身的可复现性存疑,先解决这个再继续。**

### P1 — 墙下对照(30G)
wall_reconfirm 单对象 30G,全量写+全量校验。
- 预期:全绿(对象完整落在 36G 洞下)。
- **若 P1 都有错 → 问题不是 32G 墙,是更基础的东西,立即上报,主线全部重估。**

### P2 — 对象内交叉污染(48G,因果与 delta 测定)
单对象 48G:
1. 先写 [0,32G) 模式 L=pat(addr);
2. 再写 [32G,48G) 模式 H=pat(addr)|0x8000000000000000(高位标记);
3. 全量校验 [0,32G):找 H 模式污染;对每个污染点检验 H1(−32G)/H2(mod-4G);
4. 再全量校验 [32G,48G)。
- 墙为真的预期:低 16G 被高区写污染,delta 恒定 −32G;高区自读自洽(全绿)。
- 这一步直接给出混叠的**方向、delta、带宽**,是全文最重要的一组数字。

### P3 — 用户点名的疑点:60G / 72G 单对象
1. 单对象 60G:记录分配成败;全量写+全量校验。
   - 墙为真 → 必现大量对象内自我污染(参照 P2 的桶分布)。
   - **若全绿 → 与 P0 矛盾,说明成败取决于某种条件(分配路径?多段性?
     PA 布局?),此时加打 VA/段信息,深查。**
2. 同法复测历史记录的 72G(若 OOM 记录 74G 边界也算数据点)。

### P4 — 金丝雀跨对象污染(复核"洞上单独正常")
1. 分配金丝雀对象 C:8G,落在洞下低区(先分配,VA 靠前),写满 canary 模式;
2. 分配填充对象把洞下塞满(迫使后续分配上洞);
3. 分配高位对象 H:20G(应落在 41G 以上,打印 VA 确认),全量写;
4. 重读金丝雀 C:被污染 → "高写低"跨对象实锤,"右侧单独正常"是观测假象;
   未被污染 → 需要解释为何 P2 对象内污染而跨对象不染(PA 布局隔离?);
5. 再全量校验 H 自身。

### P5 — 失败时的兜底分析
若 P0 无法复现(vec_scan2 全绿),则:
- 用 `~/f0/va_alias_test`、`alias_read3`、`write_fate` 等现有工具重扫;
- 检查当前驱动是否与历史测试时同版本(probe 探针代码在,但全部 regkey 门控,
  stock 启动不受影响——确认启动参数干净);
- 上报,不要硬凑结论。

## 4. 判定与解读

| 结果 | 结论 | 主线动作 |
|---|---|---|
| P0 复现 + P2 测得恒定 −32G + P4 金丝雀被污染 | 墙实锤,签名确认 | 继续补丁狩猎(当前 RE/probe 路线不变) |
| P0 复现但 delta 不是 −32G | 墙在,签名错了 | RE 按新签名重找 |
| P0 不可复现,P1-P4 全绿 | **墙可能从来是观测错误** | 停止补丁狩猎,重估全部历史结论 |
| P3 全绿但 P0 失败 | 成败有条件(多段性/布局) | 定位条件,墙的定义重写 |

## 5. 操作规程

```bash
# 干净驱动重载(每个用例之间)
sudo modprobe -r nvidia_drm nvidia_modeset nvidia_uvm nvidia
echo 1 | sudo tee /sys/bus/pci/devices/0000:3d:00.0/reset; sleep 2
sudo modprobe nvidia NVreg_RegistryDwords="RmForceEnableGen2=1;RMPcieLinkSpeed=0x1;RMDisableScrubOnFree=1"
sudo modprobe nvidia-modeset; sudo modprobe nvidia-uvm
```

- **不要**使用任何 `RMCmp*` 探针 regkey(保持 stock 行为)。
- **不要**关幻影洞。
- GSP 死亡(Xid)→ FLR 恢复;`modprobe -r` 挂 D 状态 → SysRq `echo b >
  /proc/sysrq-trigger`;整机无响应 → 叫用户冷启动。
- 大对象测试吃 host RAM 做 staging 时控制分块(≤1G),host 只有 62G。
